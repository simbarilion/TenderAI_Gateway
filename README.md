# TenderAI Gateway

Асинхронный API Gateway для тендерной IT-площадки.

Сервис принимает пользовательский запрос, аутентифицирует клиента по API-ключу, применяет ограничение частоты запросов 
и проксирует запрос во внешний OpenAI-совместимый LLM API.

Тендерная специфика реализована на уровне системной инструкции и примеров запросов. 
Gateway не выполняет обработку тендерной документации самостоятельно: не анализирует загруженные файлы, 
не использует базу знаний, не реализует RAG и не рассчитывает сметы.

## Возможности и ограничения

### Возможности

- аутентификация клиентов по Bearer API-ключу;
- хранение в PostgreSQL только SHA-256-хеша API-ключа;
- проверка активности API-ключа и пользователя;
- ограничение частоты запросов пользователя через Redis;
- добавление системной инструкции тендерного AI-помощника;
- проксирование запросов во внешний OpenAI-совместимый LLM API;
- техническое логирование вызовов LLM без сохранения текста prompt и ответа;
- единый формат HTTP-ошибок;
- поддержка `X-Request-ID` для трассировки запросов;
- liveness- и readiness-проверки;
- автоматическое применение миграций при запуске Docker-контейнера.

### Ограничения

Сервис:

- не хранит API-ключи в открытом виде;
- не изменяет и не дополняет пользовательский prompt;
- не смешивает собственный rate limit с ограничениями внешнего LLM-провайдера;
- не содержит RAG;
- не выполняет парсинг документов;
- не хранит тендеры, документы или другие предметные сущности.

### Архитектура

Приложение состоит из следующих основных слоёв:

    HTTP Layer
        │
        ├── Router
        ├── Dependencies
        └── Middleware
        │
        ▼
    Service Layer
        │
        ├── Auth
        ├── RateLimit
        ├── AI
        └── Generation
        │
        ▼
    Repository Layer
        │
        ├── APIKey
        └── AIRequestLog
        │
        ▼
    Infrastructure
        │
        ├── Session (PostgreSQL)
        ├── Redis
        └── Http_client

1. GenerationService координирует основной сценарий генерации:
* проверяет rate limit;
* вызывает внешний LLM через AIService;
* преобразует ошибки провайдера в доменные исключения;
* сохраняет технический результат вызова;
* возвращает ответ HTTP-слою.

2. PostgreSQL используется для постоянного хранения пользователей, API-ключей и технических журналов
обращений к LLM.

3. Redis используется только для хранения временных счётчиков rate limit.

#### API-ключи

- В базе данных хранится только SHA-256-хеш API-ключа.
- Сырой API-ключ создаётся seed-командой и выводится в консоль только в момент создания.
- Повторно восстановить значение ключа из базы данных невозможно.

#### Статусы технического журнала

- Для ai_request_logs.status используются следующие значения:

*     success — запрос успешно обработан внешним LLM;
*     upstream_error — внешний сервис вернул ошибку или недоступен;
*     timeout — внешний сервис не ответил в установленный таймаут;
*     rate_limited — внешний провайдер ограничил частоту запросов.

- Превышение rate limit Gateway в этот журнал не записывается, 
поскольку обращение к внешнему LLM не выполняется.

### Работа с внешним LLM-провайдером

- Gateway использует OpenAI-совместимый endpoint:

```angular2html
POST /chat/completions
```

- Название переменных окружения XAI_* сохранено как контракт конфигурации приложения.

```angular2html
При использовании Groq:

XAI_API_KEY=gsk_...
XAI_BASE_URL=https://api.groq.com/openai/v1
XAI_MODEL=openai/gpt-oss-20b
```

- Для получения API-ключа Groq используется https://console.groq.com/keys

- В приложении используются **два независимых типа ключей**.

1. Пользовательский API-ключ:

*     Используется клиентом для доступа к Gateway:
*     
*     Authorization: Bearer <api_key>
*     
*     Создаётся seed-командой.

2. Серверный ключ LLM-провайдера

*     Используется Gateway для обращения к внешнему AI API: XAI_API_KEY
*     
*     Этот ключ не передаётся клиенту и не связан с пользовательским API-ключом.

### Seed-команда

- Создаёт демонстрационного пользователя (tender-analyst) и один активный API-ключ с именем Аналитик тендеров.

- При первом запуске в консоль выводится сырой API-ключ. Ключ необходимо сохранить.
В базе данных хранится только его хеш.

- При повторном запуске seed-команда не создаёт дубликат пользователя; не создаёт новый API-ключ;
не выводит ранее созданный сырой ключ.

- Локальный запуск seed:

```angular2html
poetry run seed
```

- Запуск seed в Docker

```angular2html
docker compose exec api seed
```

- Для использования ключа в Swagger откройте Authorize и вставьте значение ключа без префикса Bearer.
